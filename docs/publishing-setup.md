# Activate independent publishing

The [selected policy](publishing-policy.md) separates ready code on dev from editorial saves on content. This repository has bootstrapped the trusted controller and provisioned the content preview and dedicated publishing App. See [Task 03-01 evidence](../tasks/03-publishing-workflow-improvements/01-content-branch-preview.md) for observed runs, corrections and remaining acceptance work. Provisioning is customer-specific: a new copy must complete the migration below before editors select content or automatic publication is enabled. The repository variable is the current pause/resume authority; do not infer its value from this document.

## Provisioning contract

Provision one independent automation App per customer. Do not change the two existing Keystatic Apps, Worker secrets, callbacks or domains. Through GitHub's supported App registration, grant repository metadata read, contents write, pull requests write, actions read, checks read and workflows write. Install only on the customer repository and read back selected repositories and permissions. No administration or ruleset bypass permission is needed. Generate a private key and transfer its PEM directly into the restricted environment secret; never commit, log or put it in a public variable. The controller signs a short-lived JWT, mints a repository-scoped installation token and revokes that token in finally, using official GitHub APIs.

Create `automation` with a custom deployment branch policy allowing **only main**. Create `content` with a custom deployment branch policy allowing **only content**. Preserve preview → dev and production → main restrictions. The content environment needs no Worker secrets or Admin public build settings. The controller's job condition reads repository `PROMOTION_ENABLED`; do not store this switch only in the automation environment. Keep validation jobs read-only and without environments/secrets.

The privileged workflow checks out its trusted default-branch SHA, installs only those dependencies, and never restores an unprivileged dependency cache or downloads PR artifacts. It then exposes the App key only to the reconciliation process. Do not replace this with checkout/install from `workflow_run.head_sha`, PR-controlled scripts or a privileged PR workflow.

## Migration order

1. Keep promotion disabled. Read current rules, environments, public variables, branches, domains and callbacks; preserve unpublished work and legacy preview. Provision/read back the automation App and restricted automation environment.
2. Land the controller and CI implementation on main through the existing checked PR flow. This bootstrap requires a protected merge; pushing only to dev cannot activate a default-branch `workflow_run` controller. A request to avoid merges means stop before this step.
3. Create content from **current main**, never dev. Apply a ruleset blocking deletion and non-fast-forward updates with no bypass actors, matching dev. Keep main's strict `Required checks` (GitHub Actions integration), required PR, merge-commit-only and zero-review rules unchanged. Confirm the remote check name before editing rules. Never force-push either operating branch.
4. Provision/read back content's public origin and branch-restricted deployment environment. Keep Pages automatic Git builds disabled. Wrangler's explicit `--branch content` upload creates the content alias; Pages' disabled Git-build include list is not an Actions permission gate. No extra Admin Worker is created.
5. Synchronize main into both branches without discarding concurrent work, and run CI on content. Confirm content upload branch/SHA, canonical/RSS/sitemap URL and `X-Robots-Tag: noindex`. Content-only changes select Site and skip Admin. Legitimate main synchronization may validate Admin code, but content never deploys an additional Admin.
6. With explicit merge authorization, enable promotion and verify the two PR creation/reuse/merge paths, latest source/base checks, event propagation, conflict/failure/permission stops, controlled titles, trusted synchronization and no-diff loops. Automatic merge is a publication, so use reversible approved fixtures and record resulting run/deployment SHAs. Do not declare success from unit tests or workflow syntax alone.
7. After remote verification, update the active operating guidance and editor links to production Admin → content. Preview Admin remains for developer checks. Keep legacy preview branch/alias and every existing callback. Comprehensive deployed auth/write and recovery evidence belongs to Task 05.

## Operating the controller after activation

Every ready dev push or content save becomes a publication request. Keep unfinished code on temporary work branches. The `Publish branches` workflow reconciles both operating branches after CI completes, including reruns. It reads current state instead of blindly replaying an event. App-created PRs and App merges must produce their own PR/main CI runs; never substitute GITHUB_TOKEN writes and assume propagation.

The controller follows GitHub API 2026-03-10: after requesting PR details and confirming mergeability, it reads the documented PR merge ref and verifies its two parents; it does not depend on the removed `merge_commit_sha` response field. The controller first rejects forbidden content history, synchronizes latest main when necessary, and waits for new checks. It creates one PR per source/main pair and reuses it for later saves. It refuses draft/closed-unmerged PRs, conflicts, outdated heads/bases, missing/failed checks and unmet protections. It merges through GitHub's protected merge endpoint with an explicit expected head and deterministic Conventional Commit title. Main advancing after the final read is handled by strict base protection, not bypass or force push. Retrying reconciliation always rereads remote state.

To pause all publication, set repository `PROMOTION_ENABLED=false` or disable the workflow. A currently running mutation may finish; inspect its result before editing. For one source, mark its promotion PR draft or close it. To resume a draft, mark it ready and manually run `Publish branches` on main after checks. For a closed unmerged PR, run it on main with input `resume=dev` or `resume=content`; later pushes alone do not silently reopen a publication intentionally stopped by the operator. Workflow dispatch is reconciliation, not a protection bypass. Missing permissions/conflicts produce a failed controller run; restore approved credentials or resolve the conflict, then reconcile. Never grant bypass access to make a failed merge pass.

Inspect both the PR and production deployment run. A successful merge does not establish successful hosting deployment. Existing full recovery remains available; target-specific recovery and validated Admin artifacts are separate Tasks 02/03. Do not rely on the next unrelated push to repair a stale or failed upload.

## Editorial and schema recovery

After activation, editors use production Admin and explicitly select content. Keystatic's branch selector/prefix is not an exact-branch access restriction. Protected main rejects direct saves; App access remains repository-wide. The path guard is an operational safeguard for trusted writers, not a sandbox for untrusted MDX.

A direct content push checks every introduced commit, including code later reverted. A promotion checks the final paths against synchronized main too. Main-reachable commits are published history; a merge introducing main code must have the automation bot as author, a valid GitHub-made signature (including GitHub’s web-flow committer), two valid parents and the exact reconstructed clean merge tree. A read-only GraphQL signature query confirms both validity and `wasSignedByGitHub`; an author name or a user-made signature is insufficient. A forged message, author name or extra code in a merge is rejected. Verification/API failure fails closed.

If a stale editor form reports a branch-tip mismatch, preserve unsaved text, reload and reapply to the latest content. Resolve conflicts preserving newer changes; do not force-push. For an editorial conflict with main, preserve the intended text, align only the affected editorial files with main in an ordinary content commit, let the controller perform a clean synchronization, then reapply the desired editorial edits. Do not hand-create a code-bearing merge on content: only the verified automation merge qualifies for that exception. If resolution requires non-editorial changes, resolve those through the code/main publication path first and stop for maintainer direction rather than weakening the guard. For incompatible schemas, pause editing, publish compatible code/schema, synchronize content, deploy/verify the matching production Admin and only then resume saves. Do not create new-schema content through an unpublished preview Admin. Posts marked draft stay out of public output; Pages and settings saves are immediately eligible after checks.

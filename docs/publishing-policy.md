# Independent publishing policy

Task 00 of Phase 03, confirmed on 2026-11-12 after the maintainer delegated policy choices to the agent’s recommendation. This is the implementation contract for Tasks 01–05. The existing [repository workflow](repository-workflow.md) remains the active operating procedure until Task 01 implements the transition; it must then be updated together with customer setup and operations. No branch, protection, credential or deployment setting is changed by this policy task.

## Branches and readiness

Use `main` for production, `dev` for ready-to-publish code and maintenance, and `content` for editorial work. Create `content` from the then-current `main`, never from unpublished `dev`. Keep unfinished code on temporary work branches; merge those into `dev` when ready. Every eligible `dev` push and every editorial save to `content` requests production publication after checks. The maintainer accepted the recommended readiness policy. Post `draft` continues to exclude a Post from public output; Pages and Site Settings have no additional readiness field. Saving an existing published Post can publish its changes automatically.

Keep merge commits, zero required approvals and strict latest-base `Required checks` on `main`, with no bypass actors. Preserve deletion and force-push protection on `dev`; apply the same to `content`. Both operating branches allow ordinary direct writes. Do not delete either after promotion. A content promotion contains only editorial changes relative to current `main`, so it cannot publish unreleased dev code. A code promotion includes already published content through synchronization.

## Promotion controller

Use a separate customer-owned GitHub App, installed only on the customer repository. Selected permission contract: metadata read, contents write, pull requests write, checks/actions read for result inspection, and workflows write for synchronizing workflow-file changes. Read-back the granted endpoint-specific permissions during provisioning; stop on unsupported or insufficient access. Do not expand either Keystatic App or give the automation administration/bypass permissions. Store the automation private key only in a dedicated GitHub environment restricted to `main`; keep its public client ID in configuration. Ordinary validation jobs remain read-only with no deployment or automation secrets.

Run privileged controller code only from trusted `main`, using supported `workflow_run` completion events and manual reconciliation/retry. Inspect event metadata and GitHub API data; do not execute source-branch code, install source-branch dependencies, or consume untrusted executable artifacts. PR text and branch names are data, never shell fragments. Before implementation, verify that the trusted controller can observe new content/dev pushes and PR checks without an event gap. Default-branch bootstrap must land before enabling automation.

Use App installation tokens for PR creation, merge and synchronization. GitHub documents that ordinary `GITHUB_TOKEN` push events do not start new runs; its automated PR events may require approval. The selected App path avoids relying on suppressed events. The current repository defaults to read-only workflow tokens and does not allow Actions PR approval; do not weaken those defaults just for validation. Task 01 must demonstrate App-created PR CI, merge-triggered main CI and synchronization-triggered branch CI before claiming working automation.

Serialize controller mutations for this repository without cancelling a running mutation, and reconcile current remote state on every invocation. Allow at most one open promotion PR for each exact source/base pair. Use `gh pr create` or the official REST API with explicit same-repository head/base. Reuse open PRs; later commits update the same PR. Do not create a PR for equal trees or ancestry-only synchronization. Draft PRs and intentionally closed unmerged PRs suspend automatic recreation for that source until the operator explicitly resumes; a genuinely later publication can be resumed through reconciliation. A merged PR does not suspend the next publication.

Before merge, fetch the current source/base SHAs, ensure main is an ancestor of source, check the exact pair's successful merge-result validation, editorial eligibility, draft/closure state and required reviews. Any head/base change invalidates that decision. Use the official protected PR merge API or `gh pr merge --merge --match-head-commit <sha>` with a controller-generated subject; never use `--admin`. This is automatic merging by the controller after checks, not a requirement to manually merge. Native deferred `--auto` was considered; direct head-matched merging is selected so the controller controls the final title and rechecks each current pair. Repository `allow_auto_merge=false` can remain unchanged for this mechanism. Strict protection must reject a base race; reconcile, synchronize and revalidate rather than forcing it through.

Generate merge subjects deterministically: `chore: publish dev changes` and `chore(site): publish content changes`. Generate synchronization subjects as `chore: sync main into dev` or `chore: sync main into content`. Validate the final subject with the existing Commitlint configuration immediately before the API call; do not derive it from an editable PR title. Recheck developer commits and narrow Keystatic message exceptions independently. Allowed scopes remain only `admin` and `site`, with no scope for shared changes. No rewriting prior commits.

Failed/cancelled/missing checks, stale results, permission failures, conflicts and unexpected skipped checks stop promotion and produce a visible failed controller run. Retries must reuse current remote PRs, handle already-merged responses, and avoid duplicate merges. An operator can pause by making the PR draft or closing it, fix/reopen it and explicitly resume reconciliation. No automatic approval or protection bypass is permitted.

## Synchronization and editorial boundaries

After any main advance, merge current main into both operating branches without force pushes, using the official branch merge API or ordinary Git merge/push. Before considering either promotion, synchronize it to latest main and run fresh checks. Treat a non-fast-forward race as a retry with fresh tips; never discard a concurrent save. Conflicts stop that branch's promotion until a maintainer resolves them preserving both histories. Independent work on the other branch may proceed only if its own synchronization and checks succeed.

Editorial paths are `content/pages/**`, `content/posts/**`, `content/settings/site.yaml` and `apps/site/src/assets/images/{pages,posts,settings}/**`. For `content → main`, inspect every changed path in the PR diff against current main after synchronization. For a direct content push, inspect each new commit against its parent rather than exempting the whole push because it includes one trusted merge. Reject code/schema/workflow paths introduced by ordinary editorial commits, even when later reverted. Content is compiled MDX and editors remain trusted repository writers; this path guard is operational, not a permission sandbox or a claim that MDX is safe untrusted input.

A synchronization exemption requires the dedicated App identity plus verified merge parents and a reconstructed clean merge tree from the recorded main/source tips. A message, author name or merge flag alone is insufficient. Fast-forwarded main commits must be proven reachable from the recorded main tip. Unexpected merge trees or source movement require fresh inspection. Legitimate main code/schema changes can then reach content without accepting arbitrary executable changes disguised as synchronization. A synchronization-only result may run needed checks/previews but must not create an empty promotion PR.

Editors must refresh/reopen stale forms after synchronization and resolve save conflicts without overwriting newer content. For incompatible schema changes, pause editing, publish compatible code/schema first, synchronize content, deploy the matching production Admin, verify the schema/editor contract, then resume editorial saves. Do not save new-schema content through an Admin built from unpublished dev. Backward-compatible migrations should be staged; do not solve schema incompatibility by combining unpublished code into a content PR.

## Previews, gates and recovery

Keep existing production origins/callbacks. Selected origins are `https://dev.astro-keystatic-starter-site.pages.dev` for code and `https://content.astro-keystatic-starter-site.pages.dev` for editorial Site previews; production remains `https://astro-starter.hyeongjongkim.dev`. Build canonical/RSS/sitemap origins from the matching public variable, and verify Pages preview noindex headers. Git builds remain disabled; upload explicit branch and source SHA with Wrangler.

Editors use the existing production Admin and select `content` after migration, keeping editorial schema aligned with main. The preview Admin remains for developer validation against dev/work branches. No additional Admin Worker is needed. Schema-changing releases must follow the pause/compatibility procedure above until the production Admin and synchronized content are verified. Both existing Admin Apps keep their callbacks and secrets. Keystatic selection is not an exact-branch permission restriction; do not claim a prefix enforces one branch.

Keep `preview` GitHub environment restricted to `dev`, `production` to `main`, and add an editorial Site deployment environment restricted to `content`. It needs its own Site URL and deployment configuration; it does not need Worker OAuth secrets. Restrict the separate automation environment to main. PR validation receives only public configuration. Each customer owns these settings, the new App and deployment credentials.

Preserve the existing affected-target matrix: docs only skip both, editorial/Site changes select Site, Admin changes select Admin, shared/dependency/CI/unknown changes select both. Content synchronization can carry legitimate main code; calculate preview impact accordingly, but do not deploy an additional content Admin. PRs validate and never deploy. Branch pushes deploy previews after checks, main pushes deploy affected production targets after checks. Promotion need not wait for preview upload success; passing CI and a merge do not prove production deployment succeeded.

Serialize each app/environment deployment independently. A Site failure must not block eligible Admin deployment and vice versa. Preserve failed/skipped/stale target visibility. Verify current source SHA and environment public settings against the validated artifact before upload. Task 03 will reuse independently validated preview/production Admin artifacts. No secrets belong in these artifacts.

Selected recovery is operator-triggered after a visible failure, not an unbounded automatic retry. Retry failed jobs only while their source remains current; otherwise dispatch current-head full validation with explicit Site, Admin or both targets. A docs-only commit cannot erase a pending affected deployment. Keep full recovery as a safe default and retain source/settings checks and per-target serialization. Recovered Admin-only deployment must not unnecessarily rebuild/redeploy Site. Exact failure/skip/recovery behavior is implemented in Task 02 and deployed in Task 05.

Dependency-update PRs target dev and must run read-only PR checks, including workflow/tooling changes; add `pull_request` validation targeting dev before enabling updates. Selected eligibility is manual maintainer review/merge of those PRs, followed by the normal automatic dev promotion. Do not silently auto-merge a dependency update into dev, because that becomes a production publication request.

## Migration, rollback and scenario review

First provision the dedicated automation App through the owner. Then bootstrap trusted controller code/checks on main through the current protected PR flow; create content from current main; configure content protection/environment/origin; synchronize both branches; validate previews and controller events; update editor links/selection; and only then enable automatic promotion. Retain the historical preview branch, alias, domains and OAuth callbacks. It has no unique commits as of this inspection, but this does not establish that external links no longer use it. Retirement requires a separate explicit decision.

To stop automation, disable the controller and revoke its App token/key if needed; keep protections and deployed output. Revert a bad publication through a checked PR and then synchronize both branches. Resume the previous dev/manual promotion workflow only after reconciling unpublished content, rather than deleting content or force-resetting history. Artifact and full-target recovery handle failed deployments, not Git history rewriting.

| Scenario                                                                | Required outcome                                                                            |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Dev contains unpublished code; content changes a Page                   | Content starts from main, synchronizes main only, and publishes only editorial changes      |
| Two rapid content saves while checks run                                | Reuse one PR; old-head checks cannot authorize latest-head merge                            |
| Dev publishes while content PR is ready                                 | New main invalidates the prior base; synchronize content and revalidate                     |
| Main-to-content includes code                                           | Verify trusted ancestry/tree, allow synchronization, validate affected preview; no empty PR |
| Editorial commit touches code then reverts it                           | Per-commit direct-save guard fails despite an editorial-only final diff                     |
| A fake sync commit includes workflow changes                            | Identity/parents/reconstructed-tree verification fails; visible stop                        |
| Content needs an unpublished schema                                     | Pause and publish compatible schema/Admin first; never promote dev through content          |
| Conflicting editorial/developer changes or stale form                   | Stop affected promotion and require conflict resolution preserving newer edits              |
| Draft/closed PR, failed/cancelled/missing checks or missing permissions | No merge; visible state and explicit resume/retry                                           |
| No publication diff or repeated controller event                        | No duplicate/empty PR, merge or synchronization loop                                        |
| Reviewed dependency update merges into dev                              | Fresh dev promotion runs automatically; review was required before dev entry                |
| Site fails while Admin is eligible; a docs push follows                 | Admin remains independent; operator can recover Site at current head                        |
